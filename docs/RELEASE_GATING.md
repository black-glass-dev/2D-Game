# Downloadable APK Release Gate

## Policy

A GitHub pre-release APK is a player-downloadable in-place update, not merely an export artifact. Starting with the Batch 13 workflow policy, it may be created only when all of these checks succeed in the same run:

1. source/static/native checks;
2. a fresh editor-import scan followed by a clean second editor-import pass with no parse/autoload failure, then Android debug export, ZIP integrity, and APK signature verification;
3. normal-Boot gameplay-flow checks and renderer capture gates;
4. the Android emulator install/launch step, including acceleration/readiness checks, install output, package/foreground proof, and crash-log scan; and
5. successful upload of the qualifying seven-day tested-build evidence bundle before candidate publication.

The runner attempts the emulator-runner documented KVM udev rule, then verifies writable `/dev/kvm`; when the hosted image rejects a live reload/trigger, it records that condition and applies the previously verified direct node-permission fallback before requiring access. It installs and verifies the narrowly required `libpulse0` runtime library after a pre-launch diagnostic captured QEMU's missing `libpulse.so.0` loader error. CI run 39136026161 verified that QEMU and the AVD then load, but still timed out at the bounded 600-second boot allowance; its failure remains release-blocking. The gate still requires emulator hardware acceleration. The source gate additionally validates the landscape Boot entrypoint, signed `com.operationredline.outpost` export identity, playable Desert profile, locked Highrise resource, and recorded permissive asset provenance before any candidate step can be reached. After the prior API-30 AOSP ATD configuration continued to time out with KVM, the workflow now probes the action's documented API-29/default x86_64 baseline with `disable-linux-hw-accel: false`, a bounded 600-second allowance, and otherwise the action's documented defaults. Because the runner separately executes every YAML `script` line as `sh -c`, the workflow invokes one tracked POSIX probe file through `$GITHUB_WORKSPACE`; a separate workspace-absolute pre-launch hook records the post-AVD/pre-boot boundary. It also requests a QEMU guest-serial file for boot-timeout analysis, though run 39203792018 did not materialize one. CI runs [39250923376](https://github.com/islamyousuf032-glitch/2D-Game/actions/runs/39250923376) and [39259336341](https://github.com/islamyousuf032-glitch/2D-Game/actions/runs/39259336341) subsequently passed every source/import/export/normal-Boot/capture gate; the latter also exercised the expanded M6 foundation contracts. The unchanged hosted API-29/default/x86_64 emulator still timed out during boot. Candidate publication was skipped and artifact upload remained quota-blocked; this remains release-blocking and is not emulator or physical-device evidence. The script uses workspace-absolute APK/log paths and persists traced command logs plus failure-only branch diagnostics rather than splitting loops/conditionals across action inputs. After boot it saves the exact `adb install -r` output, confirms the package path, starts the app, requires a resumed `com.operationredline.outpost` activity, and scans its logcat. The tested-build evidence upload now precedes publication, has the stable `tested_build_evidence` identifier, and must also succeed in the same run; the release step explicitly requires the `android_export`, `gameplay_smoke`, `android_emulator`, and `tested_build_evidence` outcomes to be `success`. A quota/error-blocked upload therefore skips candidate publication rather than leaving a player-downloadable release without its qualifying evidence. `tools/validate_project.py` rejects source changes that remove the named emulator gate, its acceleration/install/foreground evidence contract, or the evidence-storage publication condition from the workflow.

## In-place update compatibility

The workflow continues to use the existing package identifier and restores/caches the persistent `operation-redline-debug.keystore`. This preserves the package/signing prerequisites for Android's `adb install -r` update path. It does not prove a device update unless the emulator/device install gate actually succeeds.

For a real attached device, `docs/capture_physical_android_qa.sh` collects the exact `adb install -r` output, APK SHA-256, device facts, package lookup, launch/resumed-activity data, and bounded logcat. It does not classify a run; `docs/PHYSICAL_ANDROID_HANDOFF.md` requires a named reviewer to complete and validate all D01–D12 rows separately.

## Historical candidate status

Earlier workflow revisions could publish pre-release candidates after export/headless success even when the Android emulator timed out. Those historical releases are retained as auditable records and are not retroactively relabelled or removed in this batch. They are **not** physical-device-tested deliveries and must not be offered as such. The new gate applies to every future candidate release.

## Evidence boundary

Artifact upload quota and hosted-emulator availability remain independent infrastructure risks. A quota-blocked archive is not an APK delivery and now prevents candidate publication because qualifying evidence must upload first. An emulator timeout is not a passing device result. A successful future release created through this gate still represents emulator evidence; physical-device testing is separately recorded.

The Android workflow retains an artifact for seven days only when export/normal-Boot QA fails or the Android launch gate succeeds; a hosted-emulator-only timeout no longer creates another debug-APK archive. CI run 39271155212 confirmed that the upload is skipped on that timeout. `docs/ARTIFACT_RETENTION.md` records the legacy storage audit. Its legacy cleanup is a separate manually dispatched, confirmation-gated workflow and does not alter source commits, releases, or this launch gate; GitHub requires it to exist on the default branch before dispatch. After any future dispatch, the read-only `tools/audit_legacy_artifacts.py --verify-cleanup` command must independently confirm no active exact-name pre-cutoff candidates remain.
